# Amazon S3

Amazon S3 (Simple Storage Service) is object storage, not a filesystem or a block device — there is no real directory tree underneath it. A bucket is a flat namespace of keys, and each key maps to an object (the bytes, plus metadata). The "folders" you see in the console are purely a UI convention: a key like `images/2024/photo.jpg` is really just one string with slashes in it, and the console groups keys by common prefixes to simulate a hierarchy. This matters technically because operations like "list objects under a prefix" are prefix scans over a sorted key space, not directory traversals, and it's why S3 performance guidance historically focused on key-naming/prefix distribution rather than "folder depth."

Objects are stored redundantly across multiple Availability Zones within a region (except the One Zone-IA class, which intentionally trades that redundancy for a lower price). Since December 2020, S3 provides strong read-after-write consistency for all requests — including overwrite PUTs and DELETEs. This is a common outdated interview trap: older material describes S3 as "eventually consistent" for overwrites, but that has not been true for years; a GET immediately after a successful PUT (even an overwrite of an existing key) now always returns the latest data.

S3 storage classes let you trade retrieval latency/cost for storage cost: S3 Standard (frequent access, millisecond latency), S3 Intelligent-Tiering (automatically moves objects between access tiers based on observed access patterns, with no retrieval fees and a small monitoring fee — good when access patterns are unknown or unpredictable), S3 Standard-IA and S3 One Zone-IA (infrequent access, cheaper storage but per-GB retrieval fees and minimum storage duration charges), and the Glacier storage classes (S3 Glacier Instant Retrieval, S3 Glacier Flexible Retrieval, S3 Glacier Deep Archive) for archival data, covered in more detail in [s3-glacier.md](./s3-glacier.md).

Access control is layered: bucket policies (resource-based IAM policies attached to the bucket, evaluated alongside identity-based policies), IAM policies (attached to users/roles), and legacy ACLs (object- or bucket-level, largely discouraged now — S3 Object Ownership can disable ACLs entirely so bucket policies are the sole access mechanism). Encryption at rest comes in three flavors: SSE-S3 (S3 fully manages the keys), SSE-KMS (keys live in KMS, giving you audit trails via CloudTrail and per-key IAM control, but KMS API call volume can become a throughput bottleneck under very high request rates unless you request a quota increase), and SSE-C (you supply the key on every request; AWS never stores it). Presigned URLs let you grant time-limited access to a specific object using your own credentials' signature, without making the object or bucket public — this is the standard pattern for letting a browser or mobile client upload/download directly to/from S3 without proxying through your backend.

For large objects, multipart upload splits the object into parts uploaded independently (and in parallel, with retry-per-part instead of retry-the-whole-object). AWS recommends multipart upload above roughly 100 MB and requires it above 5 GB, since a single PUT is capped at 5 GB; the absolute maximum object size (via multipart) is 5 TB.

## Examples

```bash
# Create a bucket with versioning enabled to protect against accidental overwrite/delete
aws s3api create-bucket --bucket my-app-artifacts-prod --region us-east-1
aws s3api put-bucket-versioning \
  --bucket my-app-artifacts-prod \
  --versioning-configuration Status=Enabled
```
Versioning keeps every prior version of an object instead of destroying it on overwrite, and turns a DELETE into a delete marker rather than a permanent removal — recoverable by deleting the marker.

```json
// Bucket policy: allow a specific role to read objects under a prefix, deny everything over plain HTTP
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAppRoleRead",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:role/app-service-role" },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-app-artifacts-prod/public-assets/*"
    },
    {
      "Sid": "DenyInsecureTransport",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::my-app-artifacts-prod",
        "arn:aws:s3:::my-app-artifacts-prod/*"
      ],
      "Condition": { "Bool": { "aws:SecureTransport": "false" } }
    }
  ]
}
```
Resource-based bucket policies are the standard way to grant cross-account or scoped access without touching IAM users; the `aws:SecureTransport` deny is a common hardening pattern to reject any non-TLS request.

```js
// Generate a presigned URL so a browser can upload directly to S3 (SDK v3)
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const client = new S3Client({ region: "us-east-1" });
const command = new PutObjectCommand({
  Bucket: "my-app-artifacts-prod",
  Key: `uploads/${crypto.randomUUID()}.png`,
  ContentType: "image/png",
});
const url = await getSignedUrl(client, command, { expiresIn: 300 }); // valid 5 minutes
```
This avoids routing large file uploads through your application server — the client uploads straight to S3 using a short-lived signed URL, and your backend never touches the object bytes.

## Common Pitfalls / Gotchas

- Treating S3 as a general-purpose filesystem — there's no atomic rename (a "move" is actually a copy + delete), and listing a "directory" with millions of keys under one prefix is a paginated scan, not an O(1) lookup.
- Forgetting that deleting an object in a versioned bucket only adds a delete marker — the old versions (and their storage cost) still exist until explicitly deleted, which surprises people expecting DELETE to free up storage immediately.
- Enabling SSE-KMS on a high-throughput workload without checking KMS request quotas — every encrypt/decrypt call hits the KMS API, and default quotas can throttle S3 requests under load.
- Making a bucket public (or leaving default ACLs permissive) without realizing S3 Block Public Access is off — this is one of the most common real-world data breach causes, which is why AWS now defaults Block Public Access to on for new buckets.
- Assuming eventual consistency still applies and building unnecessary retry/backoff logic for read-after-write — that hasn't been needed since the 2020 strong consistency change, though cross-region replication and CloudFront caching still have their own propagation delays.
- Not setting a lifecycle policy on a bucket that accumulates logs or temp uploads — objects sit in S3 Standard indefinitely, quietly inflating the bill, when they could transition to IA/Glacier or expire automatically.

## Interview Questions & Answers

**Q: Is S3 strongly or eventually consistent?**
A: Strongly consistent, for all operations, since December 2020 — a GET or LIST immediately after a successful PUT, overwrite PUT, or DELETE always reflects that change. Before that date S3 was eventually consistent specifically for overwrite PUTs and DELETEs (new-object PUTs were already read-after-write consistent), which is why older resources describe it differently.

**Q: What's the difference between a bucket policy and an IAM policy for controlling S3 access?**
A: An IAM policy is identity-based — attached to a user, group, or role, defining what that identity can do, potentially across many resources/services. A bucket policy is resource-based — attached directly to the bucket, defining who (including other AWS accounts) can access it. They're evaluated together; a request is allowed only if neither an applicable IAM policy nor the bucket policy denies it, and at least one of them explicitly allows it. Bucket policies are the standard tool for cross-account access grants.

**Q: When would you choose S3 Intelligent-Tiering over manually managing lifecycle rules between storage classes?**
A: When access patterns are unpredictable or unknown in advance. Intelligent-Tiering monitors each object and automatically moves it between frequent-access and infrequent-access tiers (and optionally archive tiers) with no retrieval fees, at the cost of a small per-object monitoring fee. Manual lifecycle rules are cheaper and more predictable when you actually know the access pattern (e.g., "logs are never read again after 30 days") — in that case a scheduled transition to IA or Glacier beats paying the monitoring fee.

**Q: How does multipart upload work and why does it matter for reliability, not just speed?**
A: The object is split into parts (each a separate PUT with a part number), which can upload in parallel and be retried individually on failure — you don't have to re-upload a 4 GB file just because one chunk timed out. The upload isn't visible as an object until you send a CompleteMultipartUpload request referencing all successfully uploaded part ETags; if you abort or never complete it, S3 can leave incomplete parts accumulating storage cost, which is why it's standard practice to set a lifecycle rule that aborts incomplete multipart uploads after N days.

**Q: How would you serve private S3 content to end users without making the bucket public?**
A: Either presigned URLs (time-limited, signed with your credentials, generated on demand by your backend) for direct, short-lived access, or CloudFront with an Origin Access Control (OAC) in front of a bucket that blocks all public/direct S3 access, using CloudFront signed URLs/cookies for broader access control, caching, and lower latency at scale. The bucket itself stays fully private in both cases.
