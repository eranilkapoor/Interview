# MongoDB Interview Preparation

MongoDB is the most widely used document-oriented NoSQL database, and interviews on it tend to probe three layers at once: whether you understand the document data model well enough to design a sane schema, whether you can write correct and efficient queries (CRUD and aggregation), and whether you understand how MongoDB behaves as a distributed system in production — replication for availability, sharding for horizontal scale, and the consistency/durability tradeoffs both introduce. This folder covers all three layers, each topic with a real conceptual explanation, working shell/query examples, common pitfalls, and interview Q&A.

## Interview Questions & Answers — Curated

**Q: What is a document database, and how does it differ from a relational database? (Beginner)**
A: A document database stores self-contained, semi-structured records (documents) rather than flat rows in rigidly-typed tables. MongoDB documents can nest objects and arrays and don't require every document in a collection to share the same fields. Relational databases normalize data across many tables and reconstruct related data via joins at query time; MongoDB favors embedding related data into one document specifically to avoid needing a join for common reads.

**Q: What is BSON? (Beginner)**
A: Binary JSON — the binary-encoded format MongoDB actually stores documents in. It's a superset of JSON's type system (adding `Date`, `ObjectId`, `Decimal128`, binary data, 64-bit integers) and is more compact and faster to traverse than parsing text JSON, since field lengths are encoded up front.

**Q: What is the `_id` field and how is it generated by default? (Beginner)**
A: The mandatory, immutable primary key of every document, automatically indexed. If not supplied, MongoDB generates a 12-byte `ObjectId` (timestamp + machine/process identifier + incrementing counter), which is unique without a central sequence and roughly sortable by creation time.

**Q: When would you embed related data versus reference it? (Beginner/Intermediate)**
A: Embed when the data is small, bounded, and always read together with its parent (an address on an order). Reference when the data is large, shared across many documents, updated independently, or could grow unboundedly (a customer's full order history) — referencing avoids duplication and keeps any single document from growing without bound.

**Q: How do MongoDB's aggregation pipeline stages map to SQL concepts? (Intermediate)**
A: `$match` is like `WHERE`, `$group` (with its `_id` grouping key and accumulators like `$sum`/`$avg`) is like `GROUP BY`, `$project` is like a `SELECT` field list, `$sort`/`$limit`/`$skip` handle ordering and pagination, and `$lookup` performs a left-outer-join-like operation against another collection, always returning an array even for a 1:1 relationship.

**Q: What does `explain()` tell you, and how do you use it to tell if a query is efficient? (Intermediate)**
A: It returns the actual execution plan: `IXSCAN` means an index was used, `COLLSCAN` means the whole collection was scanned. You compare `totalDocsExamined` to `nReturned` — a healthy, selective query examines close to what it returns; a large gap signals a missing or poorly-selective index.

**Q: What is the "prefix rule" for compound indexes? (Intermediate)**
A: A compound index on `{ a: 1, b: 1, c: 1 }` serves queries filtering on `a` alone, `a` and `b`, or all three — any left-to-right prefix — but not `b` or `c` alone without `a`. Field order should match real query patterns, typically equality fields before range/sort fields.

**Q: What is a covered query? (Intermediate)**
A: A query where every field it needs (filter and projection) is present in the index itself, so MongoDB answers it without ever reading the underlying document — visible in `explain()` as `totalDocsExamined: 0`.

**Q: How does a MongoDB replica set elect a new primary? (Intermediate)**
A: Using a Raft-derived consensus protocol: when the primary becomes unreachable, remaining members hold an election, and a candidate needs votes from a majority of all voting members (not just reachable ones) to win. That majority requirement is why replica sets use an odd member count — it avoids ties and ensures at most one side of a network partition can ever elect a primary, preventing split-brain.

**Q: What is the oplog and what role does it play in replication? (Intermediate)**
A: A capped collection on the primary recording every write operation in order. Secondaries continuously tail and apply oplog entries to stay in sync. Because it's capped, a secondary that falls behind longer than the oplog's retention window can't catch up incrementally and needs a full resync.

**Q: What's the difference between `w: 1` and `w: "majority"` write concern? (Intermediate)**
A: `w: 1` acknowledges a write once the primary applies it — fast, but that write could theoretically be lost if the primary fails before replicating it anywhere. `w: "majority"` waits for a majority of the replica set to acknowledge it — slower, but durable against a single-node failure and safe from rollback after a subsequent election.

**Q: How does sharding distribute data across a cluster? (Intermediate/Advanced)**
A: Data is partitioned by shard key into chunks — contiguous ranges (or hash buckets) of shard key values — which the balancer distributes and migrates across shards to keep them roughly even. Applications connect through `mongos`, which routes each query to the right shard(s) using chunk-to-shard metadata stored on the config servers; a query that includes the shard key targets one shard, otherwise it's broadcast to all of them.

**Q: What makes a good shard key, and what's the classic mistake? (Advanced)**
A: A good shard key has high cardinality, spreads both data and write traffic evenly, and ideally matches common query patterns. The classic mistake is a monotonically increasing key (a timestamp or default `ObjectId`) used directly — every new write lands in the highest-value chunk, concentrating all insert traffic on one shard. The fix is hashing the key or leading a compound key with a higher-cardinality, more randomly distributed field.

**Q: When would you use a multi-document transaction instead of relying on single-document atomicity? (Advanced)**
A: When an operation must atomically affect multiple documents, potentially across collections, and a partial application would be a real correctness bug — e.g., transferring a balance between two account documents, or decrementing inventory while creating an order. Since a single document's write is already atomic, and MongoDB schemas favor embedding data that changes together, transactions should be the exception rather than the default write pattern.

**Q: What versions/topologies support multi-document transactions? (Advanced)**
A: 4.0+ for replica sets, extended to sharded clusters in 4.2+. A standalone, non-replica-set `mongod` does not support them.

**Q: Why might denormalizing data (duplicating a field across documents) be the right call in MongoDB? (Advanced)**
A: When a field is read far more often than it changes, duplicating it (e.g., a customer's name embedded on each of their orders) avoids a `$lookup`/join on every read at the cost of needing to propagate updates — or accepting staleness — when the source value changes. It's a deliberate read-performance-for-write-complexity tradeoff, not an oversight the way redundancy usually is in relational design.

**Q: How would you diagnose "the app is slow" against MongoDB in production, without guessing? (Advanced)**
A: Enable the profiler (`db.setProfilingLevel(1, { slowms: 100 })`) to find which operations are actually slow, then run the worst offenders through `explain("executionStats")` to see if they're missing an index, check whether the working set still fits in RAM, and confirm the driver is using a reused connection pool rather than reconnecting per request.

**Q: What's a common mistake teams make when moving from a relational database to MongoDB? (Advanced)**
A: Porting the relational schema one-to-one — a collection per table, foreign-key-style references everywhere, constant `$lookup` joins. This discards the main benefit of the document model (fetching a whole entity in one read) without gaining a relational database's built-in referential integrity. The fix is redesigning around actual access patterns: embed what's read together, reference what's large, shared, or independently updated.

## How to Use This Folder

Start with MongoDB Overview and Documents and Collections to ground the data model, then CRUD Operations and Aggregation Pipeline for the query layer. Indexes and Performance Tuning go together — read them back to back. Schema Design ties the data-model and query-pattern decisions together and is worth revisiting after the others. Finish with Transactions, then Replication and Sharding, since both distributed-systems topics build on schema and consistency concepts covered earlier. For each topic, practice explaining it out loud: the core idea, a real example, the main tradeoff, and how you'd debug or verify it — that's the structure interviewers actually probe for.
