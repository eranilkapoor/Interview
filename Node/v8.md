# V8

Node.js embeds V8, the same open-source JavaScript/WebAssembly engine that powers Google Chrome, to actually parse, compile, and execute JavaScript, and to manage its memory. Everything about how fast your Node code runs, how much memory it uses, and how garbage collection pauses affect your event loop traces back to V8's internals — this is genuinely part of "Node internals" even though V8 itself isn't Node-specific, because Node's async I/O model (libuv) is layered on top of, and interacts with, V8's single-threaded execution.

V8 compiles JavaScript in a tiered pipeline rather than interpreting it naively every time. Code starts out running through **Ignition**, a bytecode interpreter, which executes quickly with low startup overhead and also collects type feedback about how functions are actually being called (what shapes of objects, what types of arguments). Functions that run often ("hot" functions) get handed to **TurboFan**, V8's optimizing JIT (just-in-time) compiler, which uses that collected type feedback to generate highly optimized native machine code specialized for the shapes/types actually observed — for example, assuming a function is always called with numbers, and generating fast numeric-only machine code. If a function is later called in a way that violates those assumptions (e.g., previously all-numbers, now called with a string), V8 "deoptimizes" it, discarding the optimized code and falling back to the interpreter/re-optimizing later — repeated deopt/reopt cycles ("polymorphism"/"megamorphism" in hot code) are a real performance smell.

A closely related concept is **hidden classes** and **inline caching**: V8 doesn't store JS objects as generic hash maps; instead, it dynamically creates internal "hidden classes" (also called "Maps" internally, unrelated to the JS `Map` type) that describe an object's shape (which properties it has, in which order). Objects with the same shape share a hidden class, which lets V8 use fast, offset-based property access instead of hash lookups, and lets call sites cache ("inline cache") the fastest access path for a given shape. Adding properties to an object in different orders, or dynamically deleting properties, produces different hidden classes for objects that "look" similar in your code, defeating this optimization — a common piece of practical advice is to always initialize all of an object's properties in the constructor, in a consistent order.

Memory management is V8's other major responsibility, via a generational, mostly-automatic garbage collector. Most objects die young, so V8 splits the heap into a small **young generation** (further split into "nursery" and an intermediate space), collected frequently with a fast, cheap **Scavenge** algorithm, and a larger **old generation** for objects that survive multiple young-generation collections, collected less often with a more expensive **mark-sweep-compact** algorithm. The `node:v8` module exposes this machinery to your code: `v8.getHeapStatistics()` reports heap size/limits, `v8.getHeapSpaceStatistics()` breaks it down by generation/space, and `v8.writeHeapSnapshot()` dumps a snapshot loadable in Chrome DevTools for finding memory leaks. The `--max-old-space-size` CLI flag (in MB) caps how large the old generation is allowed to grow before V8 aggressively collects or the process runs out of memory and crashes — a common production tuning knob for containerized Node apps with limited memory.

## Examples

```js
// Inspecting V8 heap statistics and memory limits at runtime
import v8 from 'node:v8';

const stats = v8.getHeapStatistics();
console.log({
  totalHeapSizeMB: (stats.total_heap_size / 1024 / 1024).toFixed(1),
  usedHeapSizeMB: (stats.used_heap_size / 1024 / 1024).toFixed(1),
  heapSizeLimitMB: (stats.heap_size_limit / 1024 / 1024).toFixed(1), // capped by --max-old-space-size
});

// Per-space breakdown (new space = young gen, old space = old gen, etc.)
for (const space of v8.getHeapSpaceStatistics()) {
  console.log(space.space_name, (space.space_used_size / 1024).toFixed(1), 'KB used');
}
```

```js
// Writing a heap snapshot for offline analysis in Chrome DevTools (Memory tab -> Load)
import v8 from 'node:v8';

function leakySubscribers() {
  const subscribers = [];
  return {
    subscribe(cb) { subscribers.push(cb); }, // never removed -> classic leak pattern
  };
}

const bus = leakySubscribers();
for (let i = 0; i < 100_000; i++) {
  bus.subscribe(() => {}); // simulate accumulating references
}

const snapshotPath = v8.writeHeapSnapshot(); // writes a .heapsnapshot file to disk
console.log('Heap snapshot written to', snapshotPath);
```

```js
// Demonstrating the cost of breaking V8's hidden-class optimization with inconsistent object shapes
function makePointConsistent(x, y) {
  return { x, y }; // same property order every time -> shares one hidden class
}

function makePointInconsistent(x, y) {
  const p = {};
  if (x > 0) p.x = x; // properties added conditionally / in varying order
  p.y = y;
  if (x <= 0) p.x = x;
  return p; // produces different hidden classes depending on the branch taken
}

// In a hot loop, makePointConsistent lets V8's inline caches stay monomorphic (fast);
// makePointInconsistent forces polymorphic/megamorphic property access (slower),
// because objects that "look similar" in source may have structurally different hidden classes.
```

## Common Pitfalls / Gotchas

- Confusing V8's internal "hidden class" / "Map" concept with the JavaScript `Map` object — they're unrelated; hidden classes are an internal implementation detail for object shape tracking.
- Creating objects with properties added in inconsistent order (or deleting properties later) inside hot code paths, which defeats hidden-class sharing and inline caching, silently degrading performance.
- Setting `--max-old-space-size` too low for a workload's actual needs, causing frequent, expensive garbage collection pauses (GC thrashing) as V8 struggles to stay under the limit, or an outright out-of-memory crash.
- Assuming `--max-old-space-size` caps *total* process memory — it only bounds the old generation of the V8 heap; total RSS also includes the young generation, `Buffer`/off-heap allocations, native addons, and thread stacks, so real memory usage can still exceed the flag's value.
- Treating a function's first invocation as representative of production performance — V8 needs "warm-up" time (running through Ignition, gathering type feedback, get optimized by TurboFan) before it reaches steady-state speed, which matters for benchmarking and for short-lived serverless functions.
- Writing polymorphic functions (called with wildly different argument shapes/types) in performance-critical hot paths, causing repeated deoptimization/reoptimization cycles.
- Forgetting that `v8.writeHeapSnapshot()` pauses the event loop and can produce very large files on a big heap — not something to call casually in a hot path or frequently in production.
- Assuming Node's garbage collector runs in a separate thread — major GC phases (like mark-sweep-compact on the old generation) can still cause observable pauses on the main thread, which matters for latency-sensitive applications.

## Interview Questions & Answers

**Q: What is V8's role in Node.js, and how does it relate to the event loop?**
A: V8 is the JavaScript engine — it parses, compiles (via Ignition and TurboFan), and executes JS, and it owns the heap and garbage collector. Node layers libuv's event loop and async I/O on top of V8's single JS execution thread; V8 itself doesn't provide the event loop or async I/O, it's purely responsible for running JavaScript and managing the objects it creates. Anything that blocks V8's single thread — including a GC pause or a long synchronous computation — blocks the event loop too.

**Q: Explain V8's tiered compilation (Ignition and TurboFan) in your own words.**
A: JavaScript first runs through Ignition, a bytecode interpreter that starts fast with low overhead and, while it runs, collects feedback about the actual types and object shapes being used. When a function runs often enough to be considered "hot," TurboFan compiles it into optimized native machine code specialized for the types observed. If later calls violate those assumptions, V8 deoptimizes back to the interpreter. This tiered approach balances fast startup (interpreter) against peak throughput (optimizing compiler) without needing to guess types ahead of time.

**Q: What is a "hidden class" in V8, and why does object property order matter for performance?**
A: A hidden class is V8's internal representation of an object's shape — which properties it has and in what order — that lets V8 do fast, offset-based property access and cache ("inline cache") the fastest path at a given call site, instead of doing a generic hash-map lookup every time. Objects created with the same properties added in the same order share a hidden class; if you add properties in different orders across instances (or delete/re-add them), V8 has to create separate hidden classes for what look like "the same kind" of object in your code, which defeats inline caching and makes property access slower.

**Q: Describe Node's/V8's garbage collector at a high level.**
A: It's a generational collector based on the observation that most objects die young. New objects go into a small young generation, collected frequently and cheaply via a Scavenge algorithm (copying live objects, discarding the rest). Objects that survive several young-generation collections get promoted to the old generation, which is collected less frequently but more expensively using mark-sweep-compact (marking reachable objects, sweeping/reclaiming dead ones, and periodically compacting to reduce fragmentation). This design minimizes the cost of collecting short-lived objects, which dominate typical JS workloads.

**Q: What does `--max-old-space-size` control, and why would you tune it in production?**
A: It sets, in megabytes, the maximum size V8's old generation heap is allowed to grow to before it triggers aggressive garbage collection (and eventually an out-of-memory crash if it can't free enough). It's commonly tuned in containerized deployments to keep Node's heap usage within the container's memory limit — if left at V8's default (which scales with available system memory), Node might try to grow its heap beyond what the container actually has, leading to the OOM killer terminating the process instead of V8 managing its own limit gracefully.
