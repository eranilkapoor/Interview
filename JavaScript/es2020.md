# ES2020 (ES11)

ES2020 introduced several features that are now considered essential, everyday JavaScript. **Optional chaining (`?.`)** and **nullish coalescing (`??`)** together solve two of the most common patterns in real-world code — safely accessing possibly-missing nested properties, and providing sensible defaults only for genuinely missing (`null`/`undefined`) values rather than every falsy value (see [optional-chaining.md](./optional-chaining.md), [nullish-coalescing.md](./nullish-coalescing.md)). **`BigInt`** added a new primitive type for arbitrary-precision integers, closing a long-standing precision gap in `Number` (see [bigint.md](./bigint.md)). Dynamic **`import()`** was standardized for on-demand module loading (see [dynamic-import.md](./dynamic-import.md)).

**`Promise.allSettled()`** rounded out the family of Promise-combinator methods, resolving with the outcome (fulfilled or rejected) of every input Promise regardless of individual failures — useful when you need visibility into all results, not just an all-or-nothing outcome like `Promise.all()` provides. **`globalThis`** standardized a single, environment-agnostic way to reference the global object (`window` in browsers, `global` in Node.js, `self` in workers), removing the need for environment-detection boilerplate. `String.prototype.matchAll()` returns an iterator of all regex matches (including capture groups) for a global-flagged pattern, and `export * as ns from 'module'` added a convenient module re-export syntax.

## Examples

```js
// Optional chaining + nullish coalescing working together — the signature ES2020 combo
const user = { profile: { address: null } };
const city = user.profile?.address?.city ?? 'Unknown';
console.log(city); // "Unknown" — safely handles the missing/null chain, with a correct default
```

```js
// BigInt and globalThis
const hugeNumber = 9007199254740993n; // beyond Number.MAX_SAFE_INTEGER, exact
console.log(hugeNumber + 1n); // 9007199254740994n

console.log(typeof globalThis !== 'undefined'); // true, everywhere — browser, Node, or worker
```

```js
// Promise.allSettled() — visibility into every outcome, not just all-or-nothing
const results = await Promise.allSettled([
  Promise.resolve('ok'),
  Promise.reject(new Error('failed')),
]);
console.log(results);
// [{status:'fulfilled', value:'ok'}, {status:'rejected', reason: Error('failed')}]
```

## Common Pitfalls / Gotchas

- Continuing to use `||` for defaults instead of `??`, incorrectly overriding legitimate falsy values (`0`, `''`, `false`) — one of the exact problems `??` was introduced to solve.
- Mixing `??` directly with `&&`/`||` without parentheses — disallowed by the spec as a `SyntaxError`, requiring explicit grouping.
- Forgetting `BigInt` and `Number` can't be mixed directly in arithmetic without explicit conversion.
- Using `globalThis` and assuming it behaves identically to `window` in every respect in a browser — it does for most purposes, but code that specifically needs browser-only globals should still feature-detect rather than assume `globalThis === window` guarantees browser-specific APIs exist.

## Interview Questions & Answers

**Q: What two ES2020 operators are most commonly used together, and why?**
A: Optional chaining (`?.`) and nullish coalescing (`??`). They pair naturally: `?.` safely short-circuits to `undefined` when traversing a possibly-missing nested path, and `??` then supplies a sensible default only if the result is genuinely `null`/`undefined` — together replacing verbose manual guard chains and `||`-based defaults (which incorrectly override valid falsy values).

**Q: What problem does `Promise.allSettled()` solve that `Promise.all()` doesn't?**
A: `Promise.all()` rejects immediately if any single input Promise rejects, discarding visibility into the outcomes of the others. `Promise.allSettled()` always resolves once every input Promise has settled, giving you the fulfilled value or rejection reason for *each one individually* — useful when partial failures are expected and you need to know exactly which operations succeeded or failed.

**Q: Why was `globalThis` introduced, given `window`/`global`/`self` already existed?**
A: Before `globalThis`, referencing "the global object" portably required detecting which environment the code was running in (checking for `window`, then `global`, then `self`), since each environment used a different name. `globalThis` provides one standardized name that works identically everywhere, removing that detection boilerplate.
