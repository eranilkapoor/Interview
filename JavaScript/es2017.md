# ES2017 (ES8)

ES2017's headline feature is **`async`/`await`** (see [async-await.md](./async-await.md)) — syntax that lets Promise-based asynchronous code be written in a linear, synchronous-looking style, widely considered one of the most impactful ergonomic improvements to JavaScript since Promises themselves. Alongside it, ES2017 added several smaller but genuinely useful additions: `Object.values()`/`Object.entries()` (companions to the existing `Object.keys()`, returning an object's own enumerable values or `[key, value]` pairs respectively), string padding methods (`String.prototype.padStart()`/`padEnd()`), `Object.getOwnPropertyDescriptors()` (retrieving descriptors for *all* of an object's own properties at once, useful for correctly copying properties including their getters/setters), trailing commas allowed in function parameter lists and calls (a small syntax convenience reducing diff noise when adding a new last parameter/argument), and shared memory/atomics (`SharedArrayBuffer`, `Atomics` — enabling low-level shared-memory communication between Web Workers, a specialized, advanced feature).

`async`/`await` doesn't add any new asynchronous *capability* beyond what Promises already provided — it's syntax sugar that compiles down to Promise chains under the hood. Its significance is purely ergonomic: `try...catch` works naturally for asynchronous error handling, sequential logic reads top-to-bottom instead of nested in `.then()` chains, and debugging (stepping through code, reading stack traces) becomes noticeably more intuitive compared to equivalent raw-Promise code.

## Examples

```js
// async/await: the headline feature
async function fetchUserData(id) {
  const response = await fetch(`/api/users/${id}`); // reads top-to-bottom, no .then() nesting
  const data = await response.json();
  return data;
}
```

```js
// Object.values() / Object.entries()
const scores = { alice: 90, bob: 85 };
console.log(Object.values(scores));  // [90, 85]
console.log(Object.entries(scores)); // [["alice", 90], ["bob", 85]]

for (const [name, score] of Object.entries(scores)) {
  console.log(`${name}: ${score}`); // "alice: 90" "bob: 85"
}
```

```js
// String padding and trailing commas
console.log('5'.padStart(3, '0'));  // "005"
console.log('5'.padEnd(3, '0'));    // "500"

function example(
  a,
  b, // trailing comma allowed here — reduces diff noise when adding more params later
) {
  return a + b;
}
```

## Common Pitfalls / Gotchas

- Believing `async`/`await` is a different asynchronous mechanism from Promises — it's purely syntax sugar over them; every `async` function still returns a Promise, and `await` still relies on the same microtask-queue mechanics.
- Forgetting `Object.values()`/`Object.entries()` only return an object's *own* enumerable properties, not inherited ones — same scoping rule as `Object.keys()`.
- Using `padStart()`/`padEnd()` and forgetting the padding string can itself be multi-character and will be *truncated* to fit exactly the target length if needed (`'5'.padStart(4, 'ab')` gives `'aab5'`, not `'abab5'`).
- Overusing `SharedArrayBuffer`/`Atomics` without understanding their real complexity — genuine shared-memory concurrency between threads is an advanced, narrow-use-case feature, not something needed in typical application code.

## Interview Questions & Answers

**Q: Does `async`/`await` provide any new asynchronous capability beyond what Promises already offered?**
A: No — it's syntax sugar compiled down to Promise chains under the hood. Its value is purely ergonomic: it lets asynchronous code read in a linear, synchronous-looking style and lets you use ordinary `try...catch` for error handling, rather than requiring `.then()`/`.catch()` chaining.

**Q: What's the difference between `Object.keys()`, `Object.values()`, and `Object.entries()`?**
A: `Object.keys()` returns an array of an object's own enumerable property *names*. `Object.values()` returns an array of the corresponding *values*. `Object.entries()` returns an array of `[key, value]` pairs, which pairs naturally with destructuring in a `for...of` loop.

**Q: What are `SharedArrayBuffer` and `Atomics` used for?**
A: They enable low-level shared memory between the main thread and Web Workers (or between multiple workers), along with atomic operations (`Atomics.add`, `Atomics.wait`, etc.) to safely coordinate access to that shared memory without race conditions — an advanced feature mainly relevant to performance-critical multi-threaded computation, not typical application logic.
