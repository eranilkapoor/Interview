# Web Workers

A Web Worker is a browser API for running JavaScript on a separate OS thread, off the main UI thread, so that CPU-intensive work doesn't block rendering, user input, or Angular's change detection. The main thread and a worker do not share memory — communication happens exclusively via `postMessage()`, with the payload serialized using the structured clone algorithm (not references), meaning you're passing *copies* of data back and forth, not sharing mutable objects. This is a fundamentally different model from, say, spawning a background thread in a language with shared memory; you have to think of a worker as a separate, isolated JS environment with no access to the DOM, `window`, or anything on the main thread except what you explicitly serialize and send it.

Angular has first-class CLI scaffolding for this via `ng generate web-worker <name>` (e.g., `ng generate web-worker data-cruncher`), which creates a `<name>.worker.ts` file and automatically updates `tsconfig.worker.json` and the relevant build configuration so the CLI's build pipeline knows this file needs to be bundled as a worker entry point rather than as regular application code. In the consuming component/service, you instantiate the worker with `new Worker(new URL('./data-cruncher.worker', import.meta.url))` — the `new URL(..., import.meta.url)` pattern is what lets the bundler (esbuild, in modern Angular CLI builds) statically discover and separately bundle the worker file at build time, rather than trying to inline it into the main bundle.

It's worth being direct in an interview about *why* Angular apps rarely reach for Web Workers: most of what feels "slow" in a typical CRUD/dashboard-style Angular app is I/O-bound (waiting on an HTTP response), not CPU-bound, and Observables/`async`/`await` already handle I/O-bound waiting asynchronously on the single main thread without blocking it — there's no rendering freeze while waiting for `http.get()` to resolve, because the network wait doesn't occupy the JS call stack. Workers only help with genuinely CPU-bound synchronous work that would otherwise monopolize the main thread's event loop — parsing/transforming a large dataset client-side, image or video processing, complex client-side calculations (e.g., a spreadsheet-like recalculation engine), or heavy string/regex processing over large payloads. If you're not seeing dropped frames or an unresponsive UI during some specific operation, a worker is very likely unnecessary complexity.

The build-tooling constraint mentioned in the CLI docs is real and matters in practice: because the worker file is a separate bundle entry point, it must be known to the build system statically — you can't dynamically decide at runtime "load this arbitrary file as a worker" the way you might dynamically `import()` a lazy-loaded module; the `new URL('./file.worker', import.meta.url)` argument must be a literal (or close to it) that the bundler can statically analyze at build time. This also means TypeScript type-checking inside a worker file runs under a separate `tsconfig.worker.json`, which by default doesn't include DOM types (since there's no `document`/`window` inside a worker) — referencing DOM APIs inside a `.worker.ts` file will fail to compile unless you deliberately change that config, which is itself a signal you're trying to do something a worker fundamentally can't do (touch the DOM).

## Examples

```ts
// data-cruncher.worker.ts (generated by `ng generate web-worker data-cruncher`)
/// <reference lib="webworker" />

addEventListener('message', ({ data }) => {
  // `data` arrived via structured clone — it's a copy, not a shared reference
  // to anything on the main thread.
  const result = heavySynchronousComputation(data.numbers);
  postMessage(result); // send the result back; also structured-cloned
});

function heavySynchronousComputation(numbers: number[]): number {
  // Simulate genuinely CPU-bound work: this would block the main thread's
  // event loop (freezing the UI) if run there instead of in a worker.
  let total = 0;
  for (let i = 0; i < numbers.length; i++) {
    for (let j = 0; j < 1000; j++) {
      total += Math.sqrt(numbers[i] * j);
    }
  }
  return total;
}
```

```ts
// crunch.service.ts — spawning the worker and wrapping its callback API as an Observable
import { Injectable } from '@angular/core';
import { Observable } from 'rxjs';

@Injectable({ providedIn: 'root' })
export class CrunchService {
  runInBackground(numbers: number[]): Observable<number> {
    return new Observable((subscriber) => {
      if (typeof Worker === 'undefined') {
        // Not all environments support workers (some older browsers, and
        // notably server-side rendering has no Worker global at all).
        subscriber.error(new Error('Web Workers are not supported in this environment.'));
        return;
      }

      const worker = new Worker(new URL('./data-cruncher.worker', import.meta.url));
      worker.onmessage = ({ data }) => {
        subscriber.next(data);
        subscriber.complete();
      };
      worker.onerror = (err) => subscriber.error(err);

      worker.postMessage({ numbers }); // main thread stays responsive while this runs

      return () => worker.terminate(); // cleanup if unsubscribed early
    });
  }
}
```

This wraps the worker's message-based callback API in an Observable so consumers can use familiar RxJS composition (and get automatic cleanup via unsubscription, which calls `worker.terminate()`), rather than dealing with raw `postMessage`/`onmessage` plumbing at every call site.

```ts
import { Component, inject } from '@angular/core';
import { CrunchService } from './crunch.service';

@Component({
  selector: 'app-dashboard',
  standalone: true,
  template: `<button (click)="crunch()">Run heavy calculation</button>
             <p>Result: {{ result }}</p>`,
})
export class DashboardComponent {
  private crunchService = inject(CrunchService);
  result: number | null = null;

  crunch(): void {
    // The click handler returns immediately; the UI (including this button)
    // stays responsive the whole time the worker is computing.
    this.crunchService.runInBackground([1, 2, 3, 4, 5]).subscribe((r) => (this.result = r));
  }
}
```

## Common Pitfalls / Gotchas

- Assuming a worker shares memory/objects with the main thread — it doesn't; every message is structured-cloned (a deep copy), so mutating an object inside the worker has zero effect on the object you originally sent, and vice versa.
- Trying to reference DOM APIs (`document`, `window`, `localStorage`) inside a `.worker.ts` file — workers have no DOM access at all; this is a hard platform limitation, not a config setting you can enable your way around.
- Using `new URL('./file.worker', import.meta.url)` with a dynamically computed path (built from a variable at runtime) — the CLI's build tooling needs this to be statically analyzable to correctly bundle the worker as a separate entry point; dynamic paths typically break the build or silently fail to bundle correctly.
- Reaching for a worker to "fix" a UI freeze that's actually caused by excessive Angular change detection (e.g., an expensive pipe or a huge unvirtualized `@for` list) rather than genuine CPU-bound synchronous computation — a worker doesn't help if the bottleneck is change-detection churn on the main thread, since your component code and templates still run on the main thread regardless.
- Forgetting to call `worker.terminate()` when the work is no longer needed (e.g., user navigates away mid-computation) — the worker keeps running and consuming a thread/memory until explicitly terminated or the page unloads.
- Structured-clone limitations: not everything is serializable this way — functions, DOM nodes, and certain complex object graphs can't be passed to/from a worker; only plain data (objects, arrays, primitives, `Map`/`Set`, `ArrayBuffer`, etc.) survives the trip.

## Interview Questions & Answers

**Q: Why would you use a Web Worker in an Angular app, and why is it relatively rare?**
A: A Web Worker moves genuinely CPU-bound synchronous JavaScript work — heavy computation, large data transformation, image/audio processing — onto a separate thread so it doesn't block the main thread's event loop, which would otherwise freeze rendering and user input for the duration of that work. It's relatively rare in Angular apps because most "slowness" in typical business apps is I/O-bound (waiting on HTTP responses), and Observables/`async`-`await` already handle that asynchronously on the main thread without blocking it — there's no long synchronous computation to move off-thread in the first place.

**Q: How do the main thread and a worker communicate, and what are the implications?**
A: Exclusively via `postMessage()` on each side, with `onmessage`/an `EventListener` receiving the payload. Data passed between them goes through the structured clone algorithm — it's serialized and deep-copied, not shared by reference, so the two threads have no shared mutable state. Functions, DOM nodes, and some complex objects can't be structured-cloned; only plain data survives. This also means there's some overhead proportional to payload size on every message, so workers are best suited for coarse-grained tasks (send data, get a computed result back) rather than chatty, fine-grained back-and-forth communication.

**Q: What does `ng generate web-worker` actually set up, and why can't you just dynamically `new Worker('some/path.js')` in Angular?**
A: It scaffolds a `<name>.worker.ts` file, adds/updates `tsconfig.worker.json` (a separate TypeScript config for worker code, without DOM lib types since workers can't access the DOM), and wires the build so the worker file is recognized as a separate bundle entry point. You still instantiate it with `new Worker(new URL('./name.worker', import.meta.url))`, but that URL argument needs to be statically analyzable so the bundler can discover and correctly bundle the worker file at build time — an arbitrary runtime-computed string path isn't something the build tooling can resolve ahead of time.

**Q: If you had a genuinely CPU-heavy client-side operation, like parsing a large CSV and computing aggregates, how would you architect that in Angular?**
A: Generate a worker with `ng generate web-worker csv-processor`, move the parsing/aggregation logic into that worker file so it runs off the main thread, and in the Angular service wrap the worker's `postMessage`/`onmessage` exchange in an Observable (or a Promise) so the rest of the app can consume it with normal RxJS composition and get automatic cleanup on unsubscribe via `worker.terminate()`. The main thread stays responsive — the UI keeps rendering and accepting input — while the worker does the heavy lifting, and the component only updates once the final result message arrives.

**Q: Are Web Workers available during server-side rendering?**
A: No — the `Worker` global is a browser API and doesn't exist in the Node.js SSR environment, so code that unconditionally instantiates a worker will throw during server rendering. You need to guard worker creation (e.g., check `typeof Worker !== 'undefined'`, or gate it behind `isPlatformBrowser()`) so the server render path skips it entirely and only the client-side bootstrap actually spins up the worker.
